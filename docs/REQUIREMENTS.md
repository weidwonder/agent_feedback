# Agent Feedback 需求真相源

> 本文只写已实现的现状；还没做的事在 [TODO](TODO.md)。具体行为规则在一级子模块（见「子模块划分方式」）；架构与模块边界见 [ARCHITECTURE](ARCHITECTURE.md)；接口与数据契约见技术 spec `docs/spec/2026-09-29-agent-feedback-eng-spec.md`。

## 是什么

一套 skill 反馈通道：维护者负责的 skill 被 agent 使用、遇到问题时，agent 把结构化反馈静默提交到维护者自建的收集服务；维护者在管理界面查看与处理，维护 agent 通过查询通道按 skill 与字段取反馈。

## 为什么做

agent 使用 skill 时遇到的问题（指令与环境不符、缺能力、反复失败）原本没有渠道回到 skill 开发者手里，只留在使用者本地会话里，会话结束即消失。维护者负责的 skill 数量在增长，靠使用者主动来报的比例很低，需要 agent 代为反馈。互联网上没有满足"匿名提交、无账号、专为 agent、防滥用"的成熟方案，收集端因此自建。

## 有哪些功能

| 功能 | 一句话 | 详细规则 |
|---|---|---|
| 反馈模块 | 嵌入每个宿主 skill，教 agent 何时反馈、写什么、不许写什么，并静默提交 | [反馈模块](requirements/反馈模块.md) |
| 注入工具 | 把反馈模块放进指定 skill 的源头，加引导语，并在服务端登记该 skill | [注入工具](requirements/注入工具.md) |
| 收集服务与把关 | 公开接收提交，按登记名单、字段规则和限额把关，保存 6 个月，每天备份 | [收集服务与把关](requirements/收集服务与把关.md) |
| 管理界面 | 维护者登录后查看、筛选、标记、删除反馈，管理 skill 登记与令牌 | [管理界面](requirements/管理界面.md) |
| 查询通道 | 维护 agent 凭查询令牌按 skill 与字段取清单、取详情、标记状态 | [查询通道](requirements/查询通道.md) |

## 使用者与维护者怎么用

| 角色 | 是谁 | 怎么用 |
|---|---|---|
| 使用者 | 安装了宿主 skill 的人 | 正常使用 skill，无需做任何事；可在自己的环境里设置全局关闭开关，对所有带反馈模块的 skill 同时生效；可直接询问 agent 是否发过反馈 |
| 提交方 agent | 使用者的 agent | 按反馈模块的规则自主判断、起草并静默提交 |
| 维护者 | 项目的唯一维护者 | 配置实例并对 skill 源头运行注入工具；登录管理界面做全部管理操作；生成与撤销令牌 |
| 维护 agent | 维护者的 skill 维护 agent | 凭查询令牌取反馈清单与详情、标记状态；不能登记、启用、停用、改名 skill，不能删除反馈；只有维护者另外交给它登记令牌时才能运行注入工具 |

典型旅程：维护者对某 skill 的源头运行注入工具（放入反馈模块、加引导语、登记）并按该 skill 的正常方式发布 → 使用者的 agent 使用它时遇到问题，在任务收尾时静默提交 → 提交被接收后 1 分钟内维护者可在管理界面与查询通道查到 → 维护者或维护 agent 标记处理状态，需要时删除。

## 明确不做什么

1. 不做多作者共用的平台：只服务维护者本人负责、且经注入工具登记的 skill，不开放给其他作者登记。
2. 服务端不对反馈做任何自动处理：不自动回复、不自动分类、不自动归并、不把反馈交给任何智能能力处理。
3. 不收集对话记录、代码内容、报错原文、凭据、文件路径、可识别到个人的信息和使用者业务内容的原样（问题描述需要业务背景时只写脱敏概括）。
4. 不做使用统计：只在遇到问题时提交，不上报 skill 的正常使用情况。
5. 不向使用者展示反馈的任何过程和结果，包括是否提交、是否成功、服务是否可用；例外只有两个：使用者主动询问时如实回答；安装运行环境时由 agent 所在环境自己弹出的安装确认。
6. 服务端不检查反馈内容是否含敏感信息，只校验字段是否齐全、长度与取值是否合规。
7. 提交失败不在使用者机器上暂存，也不自动重试。
8. 管理界面只有一个维护者账号，不做多账号、权限分级和统计图表。
9. 注入工具不提供自动移除：从某个 skill 里撤下反馈模块由维护者手动完成。

## 服务质量要求

| 要求 | 内容 |
|---|---|
| 收录时效 | 一次提交被接收后，MUST 在 1 分钟内能在管理界面和查询通道里查到 |
| 服务可用率 | 按月统计 MUST ≥ 99%；由维护者另行配置的外部定时检测衡量，服务只提供健康检查地址 |
| 反馈有效率 | 按月、按 skill 统计，被标记为有效或已处理的反馈占已标记（非待处理）反馈的比例 SHOULD ≥ 50%；界面不单独展示，由维护者用筛选或维护 agent 用查询通道计算 |
| 禁写信息抽查 | 每月由维护者随机抽 20 条反馈检查是否含禁写信息，目标为 0；出现即补强反馈模块的禁写清单并删除该条 |
| 使用者无感 | 端到端场景中，除使用者主动询问外，对话里 MUST NOT 出现任何与反馈相关的提示；唯一例外是安装提交所需运行环境时由 agent 所在环境自己弹出的安装确认 |
| 拒收次数 | 按超出限额、未登记或已停用、格式不合格三类逐日可见，不设目标，用于发现共用网络地址占满额度、名称被冒用等异常 |
| 上线评测准出 | 上线前 MUST 达成：维护者准备该反馈与不该反馈场景各不少于 20 个；该反馈场景触发率 ≥ 80%；不该反馈场景误触发率 ≤ 10%；全部提交内容中禁写信息出现率为 0；任一未达标不上线。场景清单与判定口径见 [上线评测场景](report/上线评测场景.md) |

## 子模块划分方式

- **切分维度**：按产品模块，即使用者、维护者、维护 agent 各自接触到的面切；每个模块一份文件，放在 `docs/requirements/`，文件名用中文模块名。
- **切成五块**：

  | 文件 | 覆盖 |
  |---|---|
  | [反馈模块](requirements/反馈模块.md) | agent 何时反馈、提交什么、静默与如实回答、会话上限、关闭开关、禁写清单、运行环境、公开说明 |
  | [注入工具](requirements/注入工具.md) | 实例配置、注入对象与前置检查、写入内容、重复运行、失败回滚 |
  | [收集服务与把关](requirements/收集服务与把关.md) | 提交的内容与限制、限额、登记名单、拒收表现、处理状态、保留与备份 |
  | [管理界面](requirements/管理界面.md) | 登录、反馈列表与详情、标记与删除、skill 登记与改名、令牌与密码 |
  | [查询通道](requirements/查询通道.md) | 身份、取清单与详情、标记状态、不可信标注 |

- **判据**：写进子模块的是用户能感知的规则（次数、额度、上限、权限、报错表现）；表结构、内部常量、缓存等感知不到的不写，去技术 spec 与 `engineering-context/` 卡片。
- 新增规则先找对应的模块文件就地写入；新增功能则在上表增加一行并建对应文件，不另起切法，不建二级目录。
